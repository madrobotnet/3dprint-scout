# v0.7.0 계획 — 검증 근거를 설계에 연결하기

상태: 초안 (2026-10-22). 경우님과 Codex 검토 전. 0.6.x 다음 릴리스는 0.7.0부터.

## 왜

0.6.x의 `finalize.py`는 형상, 조립, 끼움, 강도 보고서가 지금 STL에 대해 맞는지 검사한다. 그런데 웨이브
컬 데모에서 사용자가 먼저 찾은 실수 네 개와 실물 출력에서 짧았던 USB-C 통로는 모두 그 바깥에서 나왔다.

| 실제로 있었던 일 | 왜 검사를 통과했나 |
|---|---|
| 컨셉에서 말로 약속한 앞 노치, 끼우는 결합, 케이블 구멍이 모델에 없었다 | 말로 한 약속은 검사 대상이 아니다 |
| 자리 높이 손 계산이 모서리 라운드를 빼서, 15 mm 케이스면 립이 폰을 못 잡았다 | 손 계산 값이 만든 형상으로 확인되지 않은 채 보고됐다 |
| 옆으로 눕혀 뽑는 띠가 4.5 mm 두께 중 1.5 mm만 베드에 닿았다 | P1은 면적만 본다 (0.8.0 범위) |
| USB-C 통로가 실제 케이블에는 짧았다 | 플러그와 케이블 치수를 재지 않고 가정했고, 그 가정 위의 끼움 검사가 PASS로 보였다 |

`strength.py`도 같은 문제가 있다. 입력이 손으로 넣은 숫자라서, 두께를 바꾼 뒤에도 옛 보고서가 그대로
통과한다(지금은 "숫자를 치수표와 같게 유지하라"는 메모만 낸다).

## 목표

`finalize.py`가 무언가를 검증했다고 말하려면, 그 근거가 **지금 설계에 연결되어 있어야** 한다. 사용자에게
약속한 기능과 사용자가 물건으로 하는 일, 강도 계산의 입력, 그리고 그 밑에 깔린 가정 치수가 대상이다.

## 범위

### A. 약속과 사용 목록 (`_verify.promises`)

사용자에게 말로 한 것을 하나의 목록에 적고, 항목마다 근거를 연결한다.

```json
"_verify": {
  "promises": [
    {"id": "seat-pm15-case", "kind": "use", "text": "케이스 낀 15 프로맥스를 올려도 립이 잡는다",
     "evidence": [{"joint": "pm15 case on seat"}]},
    {"id": "cable-out", "kind": "use", "text": "직각 USB-C 케이블을 꽂고 뒤로 뺄 수 있다",
     "evidence": [{"joint": "plug through notch"}, {"joint": "cable under sled"}],
     "assumes": ["usb-c-plug"]},
    {"id": "front-notch", "kind": "feature", "text": "앞에서 케이블이 지나갈 노치",
     "evidence": [{"joint": "cable probe through notch"}]},
    {"id": "wave-back", "kind": "look", "text": "등받이가 한 번 물결친다",
     "evidence": [{"seen": "out/preview_right.png"}]}
  ],
  "assumed": [
    {"id": "usb-c-plug", "what": "직각 USB-C 플러그 머리 13 x 8 x 9 mm, 케이블 4.5 mm", "source": "assumed"}
  ]
}
```

- `kind`
  - `use`: 사용자가 하는 일. 넣기, 꽂기, 케이블 빼기, 꺼내기, 누르기처럼 동사로 적는다.
  - `feature`: 모델에 있어야 하는 기능.
  - `look`: 모양에 대한 약속.
- `evidence`는 이미 `_verify`에 선언되어 finalize가 검사하는 것만 가리킨다. 끼움 검사(`joint`), 강도
  계산(`strength`), 통과한 시험 출력(`test_print`), `<part> <check>` 같은 검사 이름이 해당된다.
  `seen`(미리보기 이미지)은 `look`에만 허용하고, 보고서에는 "눈으로 확인"으로 적는다.
- `assumes`는 그 약속이 재지 않은 실물 치수 위에 서 있다는 표시다. `_verify.assumed`의 항목을 가리킨다.
  0.6의 `_verify.unverified`(자유 문장 목록)는 그대로 읽되 연결은 안 된다고 보고한다.

**finalize 보고서에 다섯 번째 층 `use`를 추가한다.** 형상(`geometry`)과는 따로 판정한다.

| `use` | 조건 |
|---|---|
| `verified` | 모든 약속에 통과한 근거가 있고, 가정 치수에 기대는 것이 없음 |
| `assumed` | 근거는 다 통과했지만 가정 치수에 기대는 약속이 있음. 전달 메시지 첫 줄에 이름을 대고 말한다 |
| `not verified` | 근거가 없거나, 실패했거나, 오래된 약속이 있음 |
| `not declared` | `promises` 키가 없음. 0.6 프로젝트가 여기에 해당하고, 형상 판정에는 영향이 없다 |

웨이브 컬 데모를 이 형식으로 다시 쓰면, 케이블 항목은 `assumed`로 나오고 플러그 치수를 재지 않았다는 말이
보고서 첫머리에 올라온다. 실제로 놓친 것이 바로 이것이다.

지침 변경:
- 1단계(컨셉): 컨셉 설명에 쓴 기능을 그 자리에서 `promises`에 적는다.
- 2단계: 사용자와 함께 사용 목록을 만든다. 끼워지는 실물(폰, 플러그, 케이블)은 잴 수 있으면 재 달라고
  하고, 못 재면 `assumed`에 적고 시험 출력을 제안한다.
- 4단계: 근거가 없는 약속이 남아 있으면 4단계를 끝내지 않는다.
- 6단계: `use` 층을 형상보다 먼저 말한다.

### B. 손 계산은 만든 형상으로 확인

치수표에서 손으로 계산한 값(자리 높이, 립이 잡는 깊이 같은 것)은 만든 STL에서 `fit.py`나 `measure.py`로
다시 잰 뒤에만 보고한다. 형식은 A의 근거로 연결한다. 이 항목은 지침만 바꾸고 스크립트는 바꾸지 않는다.

### C. 강도 계산과 설계 변수 연결

- `build.py`가 실제로 쓴 파라미터 값(생성 스크립트 기본값 + params.json 덮어쓰기)을 빌드 JSON의
  `parameters`에 기록한다. Python과 Blender 엔진이 대상이다. OpenSCAD는 0.7.0에서 params.json으로 넘긴 값만
  기록하고, 그 한계를 문서에 적는다.
- `strength.py --from-build out/build.json --param h=ribbon_t --param b=ribbon_w ...`: 입력을 빌드의
  파라미터에서 가져오고, 보고서에 `inputs_from`(입력 ↔ 파라미터 이름)과 그 값을 남긴다.
- finalize: `inputs_from`이 있는 보고서는 지금 빌드의 값과 비교한다. 다르면 "h는 ribbon_t=4.5로
  계산했는데 지금은 5.0"처럼 이유를 대고 검증 안 됨으로 둔다. 손으로 넣은 보고서는 0.7.0에서는 지금처럼
  열린 항목으로만 남기고(막지 않음), 0.8.0에서 막는 것을 검토한다.

### D. 사용자에게 보이는 렌더 글자를 사용자 언어로

`render.py --lang ko`: 시점 이름(ISO, FRONT, RIGHT, TOP…)을 사용자 언어로 쓴다. 캡션 한글은 이미 된다.
`preview.py`는 5x7 비트맵 글꼴이라 영어로 남기고, 그 사실을 문서에 적는다.

### E. 대화 시나리오를 실제로 돌리기 (0.6.2에서 남은 것)

`references/development.md`의 시나리오 5개에, A와 C를 확인할 시나리오 2개를 더해 실제 에이전트로 돌리고
결과(물은 것, 한 것, 마지막에 주장한 것)를 기록한다.
- 지킨 약속과 어긴 약속
- 재지 않은 치수 위에 선 사용 항목

Claude와 Codex 둘 다로 돌려 비교하면 지침이 특정 에이전트에 기대는 부분이 드러난다.

## 0.7.0에서 하지 않는 것

- 0.7.x(변경 추적): STL 변경 비교, 중요 부위 단면 미리보기, 전달 버전 관리.
- 0.8.0(출력 가능성): 파라미터 범위 테스트, 국부 벽 두께, 최소 형상과 브리지 경고, 공중에서 시작하는 면
  감지, 키 큰 부품의 베드 접촉 폭, 서 있는 물건의 안정성, 선택적 슬라이서 검사.
- 보류: 서포트 인터페이스 자동 선택.

## 완료 기준

1. 웨이브 컬 데모를 축소한 테스트 프로젝트에서 `use`가 `assumed`로 나온다. 이유에 케이블 항목과 플러그
   가정이 이름으로 나온다. 플러그 치수를 잰 값으로 바꾸면 `verified`가 된다.
2. 근거 없는 약속, 실패한 근거, 오래된 근거(STL이 바뀐 끼움 보고서)는 각각 `not verified`로 나온다.
3. `ribbon_t`를 바꾸고 강도 계산을 다시 하지 않으면 finalize가 바뀐 입력을 이름으로 대고 검증 안 됨으로 둔다.
4. `render.py --lang ko`가 한글 시점 이름으로 그린다.
5. 대화 시나리오 7개의 실행 결과가 기록되어 있다.
6. 기존 테스트와 새 테스트가 Windows와 Ubuntu, Python 3.9와 3.13, Blender 4.5와 5.2 CI에서 통과한다.

## 검토 때 정할 것

1. `use` 층을 형상과 따로 둘까, 아니면 `use`가 `verified`가 아니면 형상도 검증 안 됨으로 볼까?
   제안은 따로 두는 것이다. 형상은 "모델이 숫자와 맞는가", `use`는 "그 숫자가 사용자에게 맞는가"라서
   섞으면 둘 다 흐려진다. 대신 전달 메시지에서는 `use`를 먼저 말한다.
2. `look` 약속을 눈으로 확인한 것을 근거로 인정할까? 제안은 인정하되 "눈으로 확인"으로 따로 적는 것이다.
3. 손으로 넣은 강도 입력을 0.7.0부터 막을까? 제안은 0.7.0에서는 열린 항목만 두고 0.8.0에서 막는 것이다.
4. OpenSCAD 파라미터 기록은 0.7.0에서 params.json 덮어쓰기만 할까?
5. 시나리오는 어느 에이전트로 돌릴까? 제안은 Claude와 Codex 둘 다다.
