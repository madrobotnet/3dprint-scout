- 검토일: 2026-10-22 (Asia/Seoul)
- 대상: [`v0.7.0.md`](v0.7.0.md), `v0.7.0-plan` 브랜치
- 검토 기준 커밋: `4ca84840925b87835970aef68d9d70d70a60181d`
- 방법: 계획서와 같은 커밋의 관련 구현·문서를 정적으로 읽고 검토했다. 실행 검증이나 에이전트 시나리오 실행 결과는 아니다.
- 상태: 검토 의견. 아래 권고는 아직 합의된 설계 결정이나 구현 완료 사항이 아니다.

## 전체 판단과 범위

v0.7.0의 방향과 핵심 범위는 적절하다. 실제로 놓친 문제를 **약속 → 근거 → 현재 설계**로
연결한다는 목적이 분명하다. 다만 초안에는 **근거가 존재하고 통과했다는 것만으로 약속까지
입증했다고 판정할 수 있는 빈틈**이 있다. 구현 전에 이 경계를 정하는 것이 가장 중요하다.

A·C를 중심으로 유지하고, B의 최소 근거 연결과 E를 필수로 두는 것을 권한다. D의 렌더 언어
변경은 작은 독립 작업으로 포함해도 되지만, 검증 설계가 커지면 0.7.1로 옮기기 가장 쉬운
항목이다. 0.8.0의 출력 가능성 검사까지 당겨올 필요는 없다.

## 1. `use`는 선언한 조건에서 확인되었다는 의미여야 한다

예시의 “폰을 올려도 립이 잡는다”는 약속은 단순한 간섭 없음과 다르다. 접촉 위치, 걸리는 깊이,
빠지는 방향 등이 맞아야 한다. “케이블을 꽂고 뒤로 뺀다”도 최종 위치의 끼움 검사 두 개만으로
삽입 경로까지 입증되지는 않는다.

현재 `fit.py`에는 정적 배치와 회전 sweep이 있지만, 일반적인 삽입·인출 경로나 유연한 케이블의
굽힘을 판정하는 기능은 없다.

약속마다 최소한 **대상·사용 조건·성공 기준·근거가 확인하는 범위**를 적는 것을 권한다.
임의의 PASS 검사나 `<part> G1` 같은 일반 형상 검사를 연결했다고 사용 약속이 검증되면 안 된다.
0.7.0에 새 동작 시뮬레이터까지 넣을 필요는 없고, 검사하지 못하는 동작은 명확히 미검증으로
남기면 된다.

## 2. 가정을 측정값으로 바꾸는 전환 규칙이 필요하다

완료 기준 1은 “플러그 치수를 잰 값으로 바꾸면 verified”라고 되어 있다. 실제 측정값이
달라졌다면 프록시와 끼움 검사도 갱신되어야 한다. `source`만 변경해서 옛 PASS를 재사용하면
이번 릴리스가 해결하려는 문제가 그대로 남는다.

현재 `_verify.assumed.what`은 자유 문장이라 검사 입력과 자동 비교하기 어렵다. 치수는 최소한
**값·단위·출처·대상 식별자**로 구조화하고, 그 값을 사용한 프록시나 보고서까지 연결해야 한다.
측정 오차나 허용 범위도 기록할 수 있으면 좋다.

또한 약속의 `assumes`에만 의존하면 연결 하나를 빠뜨렸을 때 `verified`가 된다. 가정은 가능하면
**근거에서 약속으로 전파**해야 한다. 기존 `proxy: true`, `_assumptions`, `_verify.unverified` 중
관련성을 확인하지 못한 항목을 어떻게 취급할지도 정해야 한다.

측정값이 기존 가정값과 같다면 기존 계산을 재사용할 여지는 있다. 다만 실제 측정 기록과 입력
일치가 확인되어야 하며, 출처 표시만 바꾼 것을 측정이나 재검증으로 간주해서는 안 된다.

## 3. 이미지와 시험 출력도 현재 설계에 연결해야 한다

`seen: "out/preview_right.png"`는 이미지 위치만 알려 준다. 누가 무엇을 확인했는지, 현재 모델에서
만든 이미지인지는 알 수 없다.

현재 `finalize.py`의 `check_prints()`도 시험 출력의 이름·상태·메모만 읽는다. 예전 부품에서 성공한
시험 출력을 새 설계의 근거로 사용할 수 있는 상태다.

두 종류 모두 **확인 대상의 해시 또는 설계 버전, 확인한 약속, 확인 주체와 결과**가 필요하다.
시험 출력은 추가로 재료·출력 방향 등 결과를 좌우하는 조건을 기록해야 한다. 이미지가 존재하는
것과 눈으로 확인한 것은 구분해야 한다.

## 4. B의 지침 변경만으로는 A의 근거 연결을 충족하기 어렵다

B는 `measure.py`로 측정한 값을 A에 연결한다고 하지만, A의 근거 종류에는 측정 보고서가 없다.
현재 `measure.py` 출력도 측정값 중심이며, 입력 파일 해시와 목표값에 대한 PASS 판정이 없다.

다음 중 하나를 선택해야 한다.

- 0.7.0에서는 B를 보고 지침으로만 적용하고, 측정 사실만으로 `use: verified`가 되지는 않게 한다.
- 작은 `measurement` 근거 형식을 추가해 대상 해시·측정 위치/축·목표값·허용오차·실측값을 검사한다.

자리 높이 계산 실수를 이번 릴리스에서 실제로 방지하려면 두 번째가 더 목적에 맞는다.
전체 측정 시스템을 확장할 필요는 없다.

## 5. C의 실제 파라미터 기록에는 명시적인 규약이 필요하다

현재 Python 엔진은 `build(params)`에 덮어쓰기 값만 전달하고, `references/engines/python.md`의
생성기 예제는 함수 안에서 `DEFAULTS`를 합친다. 생성기 내부의 기본값·보정·파생 계산을 실행기가
일반적으로 알아낼 수는 없다. Blender는 기본값을 합치는 공통 경로가 있어 상대적으로 쉽다.

따라서 “실제로 쓴 파라미터”를 **공통 규약으로 확정한 입력값**으로 정의하고, 지원하지 않는 기존
생성기는 기록 범위가 불완전하다고 표시해야 한다. 단순히 `DEFAULTS`나 `PARAMETERS`를 찾아 합친
결과를 실제 사용값이라고 단정하면 안 된다.

강도 연결에도 다음이 필요하다.

- 어느 부품·설계에서 나온 값인지 식별하는 정보.
- 일부 입력만 연결했을 때 남은 수동 입력의 표시.
- `--h`와 `--param h=…`를 함께 주는 경우의 충돌 규칙.
- 없는 파라미터, 잘못된 타입·단위, 비유한 수의 거부.
- 재료·하중·적층 방향·지지 조건이 바뀌었을 때의 처리.

특히 같은 `ribbon_t=4.5`여도 형상에 홈을 추가하면 실제 하중 단면은 달라질 수 있다.
**파라미터 일치는 강도 계산의 입력 연결을 확인하는 것이며, 실제 형상과 계산 모델의 일치까지
증명하지는 않는다.**

## 6. 상태 집계와 작업 중단 규칙을 구체화해야 한다

| 경우 | 권고 |
|---|---|
| `promises` 누락 | 제안대로 `not declared` |
| `promises: []` | 자동 `verified` 금지. 약속 없음의 의미를 별도로 정의 |
| 실패·누락·오래된 근거와 가정이 함께 있음 | `not verified` 우선, 가정 이유도 함께 유지 |
| WARN을 사용자가 수용함 | 수용 사실을 기록하되 검사 PASS로 변환하지 않음 |
| 중복 ID·없는 참조·모호한 검사 이름 | 명시적인 선언 오류 |
| 약속을 수정하거나 삭제함 | 근거 재검토 또는 합의된 범위 변경으로 기록 |

약속별 결과도 필요하다. 전체 `use` 하나만 있으면 케이블 문제와 외형 확인 문제가 섞인다.
`use`, `feature`, `look`별 결과를 함께 보여 주고, 전체 상태가 **선언된 약속 목록에 대한 결과**라는
점을 밝혀야 한다.

“근거가 없으면 4단계를 끝내지 않는다”도 예외가 필요하다. 실물 측정이나 시험 출력이 불가능한
상황에서는 무한 대기나 불필요한 재질문을 유발한다. **검증 완료·가정에 따른 조건부 진행·미검증
시제품 전달·합의된 범위 제외** 중 어떤 상태로 다음 단계에 갈 수 있는지 정하는 편이 좋다.
수용이나 진행 허가는 검증 성공과 별개다.

## 검토 때 정할 것 5개에 대한 의견

| 질문 | 의견 |
|---|---|
| 1. `use`와 `geometry` 분리 | **분리 찬성.** 사용 조건이 미확정이라고 형상 검사 결과까지 지울 필요는 없다. 다만 `use`가 참조하는 형상 근거가 무효라면 해당 약속도 무효여야 한다. 현재 `geometry`에는 끼움·강도도 포함되므로 두 층의 정확한 책임을 문서화해야 한다. |
| 2. `look`의 눈으로 확인 인정 | **조건부 찬성.** 현재 모델에서 나온 이미지와 실제 확인 기록이 있어야 한다. 자동 검사와 사람/에이전트의 시각 확인을 보고서에서 구분하고, 사용자 취향에 관한 최종 수용과도 구분해야 한다. |
| 3. 수동 강도 입력을 지금부터 차단 | **기존 계산 실행은 허용하되, 연결되지 않은 수동 보고서만으로 새 `use` 약속을 verified로 만들지는 않는 것을 권한다.** 기존 프로젝트 호환성과 새 검증 주장에 대한 기준을 나눌 수 있다. 수동 입력 자체보다 근거와의 연결이 핵심이다. |
| 4. OpenSCAD는 덮어쓰기만 기록 | **0.7.0에서는 적절하다.** 다만 문서뿐 아니라 JSON에 `overrides only` 같은 기록 범위를 명시해야 한다. 누락된 값을 추정하지 말고, `record`나 외부 CAD 경로의 제한도 함께 정의해야 한다. |
| 5. Claude와 Codex 모두 실행 | **찬성한다.** 동일한 입력·도구·사용자 응답 조건으로 실행하고 모델 버전과 스킬 커밋을 기록해야 한다. 단순 완료 여부보다 불필요한 질문, 누락된 약속, 근거 없는 최종 주장으로 평가하는 것이 좋다. |

## 빠진 항목과 완료 기준 보완

- **시나리오 개수와 내용 수정:** 검토 기준 커밋의 `references/development.md`에는 시나리오가
  **6개** 있다. 두 개를 더하면 8개다. E에 적힌 추가 시나리오 둘은 A 중심이고, C의 “강도 입력
  변경 후 옛 보고서 거부”는 명시되어 있지 않다. 실제 최종 개수는 C의 포함 방식까지 정한 뒤 맞춰야 한다.
- **완료 기준에 역방향 테스트 추가:** 가정 치수 변경 후 옛 프록시 재사용, 이미지·시험 출력의 옛
  결과 재사용, 빈 약속 목록, 일부만 연결된 강도 입력, 파라미터는 같지만 계산 대상 부위가 바뀐
  경우를 포함해야 한다.
- **근거의 전달·재현:** 현재 소스 번들에 새 근거 보고서·이미지·측정 기록을 어떻게 포함하거나
  재생성할지 정의해야 한다. 개발 폴더에서만 참조가 성립하면 전달 후 검증을 재현하기 어렵다.
- **CI 조합 명확화:** 현재 Blender 검사는 Ubuntu에서 Python 3.11/Blender 4.5,
  Python 3.13/Blender 5.2 조합이다. 완료 기준 6을 모든 OS·Python·Blender 조합의 교차 검사로
  읽히지 않게 적는 편이 좋다.

구현 전에 우선 확정할 것은 **근거가 약속을 입증하는 조건, 가정 변경의 전파, 근거의 유효 기간,
실제 파라미터 기록 규약**이다. 이 네 가지가 정해지면 0.7.0의 목적과 구현 범위가 더 명확해진다.
