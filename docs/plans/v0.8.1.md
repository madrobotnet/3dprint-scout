# v0.8.1 계획 — 경로는 상대로, 소프트 검사 판단은 기록으로

상태: 확정 (2026-10-25). "정할 것" 넷은 모두 추천대로(경우님): `unknown` 허용, 시안 한 줄 넣기, 번들은 프록시를 지금처럼 다시 빌드, 코드는 서브에이전트 하나·지침과 확인은 총괄.

## 왜

0.8.0에서 미뤄 둔 두 가지와, 0.8.0 시나리오 재실행에서 나온 작은 두 가지다.

1. **build JSON에 이 기계의 절대 경로가 남는다.** `parts[].stl`, `parts[].validate.files[].path`,
   `.blend`, `engine_info.blend`가 Python·Blender 빌드에서 절대 경로다(OpenSCAD 빌드와 `sources`는 이미 상대
   경로). 0.8.0 재실행 9개의 build JSON 모두 그렇다. 생기는 문제:
   - 프로젝트 폴더를 옮기거나 다른 사람에게 주면 finalize가 STL을 못 찾는다.
   - 공유하는 JSON에 사용자 이름이 든 경로가 남는다.
   - 같은 이유로 `--bundle`은 프록시의 build JSON을 담지 못하고 다시 빌드한다(0.7.0에서 받아들인 우회).
2. **에이전트가 정한 P4~P6 판단이 기록되지 않는다.** finalize는 P4(브리지), P5(작은 형상), P6(바닥 모서리),
   P3(벽 검사를 건너뛴 경우)를 "UNVERIFIED (yours to decide)"로 `open`에 남긴다. Phase 5는 이를 전달 전에 정하라고
   하지만, 정한 것을 적을 곳이 없다. 그래서 정한 뒤에도 finalize는 계속 같은 줄을 낸다. 0.7.0과 0.8.0 재실행에서
   여러 번 "정했지만 기록 없음"으로 나왔고, `_assumptions`에 줄로 적은 실행도 있었다.
3. **"알아서 정해 주세요"를 시안 고르기로 받아들였다.** 선택지 질문에 딸린 부가 질문에 그렇게 답하자, 두
   실행이 시안을 스스로 고르고 시안 멈춤을 건너뛰었다(should 항목).
4. **`compensation.elephant_foot: "unknown"`.** 스키마는 `slicer`나 `model`만 적는데, 슬라이서 프리셋을 모를 때
   에이전트가 `unknown`을 썼다. 이 값을 읽는 스크립트는 없다. 지침에 정의만 없다.

## 범위

### A. 상대 경로 (코드, 판정 출력 변경)

- `build.py run`과 `record`가 build JSON에 쓰는 경로를 실행한 폴더 기준 상대 경로로 바꾼다. 대상은
  `parts[].stl`, `parts[].validate.files[].path`, `blend`, `engine_info.blend`, 그리고 `threemf` 경로와 프록시 빌드다.
  드라이브가 다른 Windows 경로는 지금처럼 절대 경로로 남긴다(`_relpath`가 이미 그렇게 한다).
- 읽는 쪽은 그대로 둔다. finalize, 번들, bambu3mf가 이미 `abspath`로 맞춰 비교하므로 상대 경로는 실행 폴더
  기준으로 풀린다. 0.8.0 이전에 만든 build JSON의 절대 경로도 계속 읽는다(호환).
- 번들: 상대 경로만 든 `build.py run --proxy` JSON은 이제 담을 수 있다. 0.7.0의 우회(다시 빌드)를 바꿀지는
  "정할 것" 3에 둔다.
- 골든 비교: 0.8.0 출력과 비교해서 바뀐 것이 경로 문자열뿐이어야 한다. 그 목록을 PR에 적는다.
- 테스트: 상대 경로로 기록되는지, 옛 절대 경로 build JSON을 읽는지, 폴더를 옮긴 뒤 finalize가 통과하는지,
  Windows에서 다른 드라이브는 절대 경로로 남는지(CI windows).

### B. 소프트 검사 판단 기록 (코드와 지침, 판정 출력 변경)

- 새 선언 `_verify.decided`: 에이전트가 정한 소프트 검사 하나에 항목 하나.
  `{"check": "sled P6", "result": "holds", "reason": "bed edges sharp; the preset's elephant-foot compensation covers them", "sha256": "<그 부품 STL의 sha256, build JSON에서>"}`
  - `check`는 finalize가 "yours to decide"로 내는 것(P3 건너뜀, P4, P5, P6)만 받는다. 하드 검사나 다른 이름은 선언 오류다.
  - `sha256`이 지금 부품과 다르면 그 판단은 낡음이다. 다시 빌드해서 모양이 바뀌면 다시 정한다(seen과 같은 방식).
  - `result`는 `holds` 또는 `warn`이다. `holds`이면 `open`에서 빠지고 보고서의 새 목록 `decided`에 이유와 함께 들어간다.
    `warn`이면 `open`에 WARN으로 남고, 사용자는 지금의 WARN처럼 받아들이거나(`_verify.accepted`) 고친다.
- 판정에 주는 영향: 소프트 검사라서 gate와 `geometry`에는 영향이 없다. 바뀌는 것은 `open`과 새 `decided` 목록이다.
  `decided`가 없는 프로젝트는 지금과 같은 출력이다.
- 지침: Phase 5 2단계의 "정하라"에 기록 방법(checks.md 표에 한 줄), outputs.md에 `decided` 설명, SKILL.md는 그대로.

### C. 지침 두 줄

- Phase 1 시안: "다른 질문에 '알아서 정해 주세요'라고 한 답은 시안을 고른 것이 아니다. 시안을 보여 주고 멈춘다."
  ("정할 것" 2)
- `elephant_foot` 값 정의("정할 것" 1).

### D. 확인

- 세 환경 테스트, CI, `agentskills validate`, 골든 비교(경로 문자열 외 0 차이).
- 시나리오: 경로와 `decided`가 닿는 넷을 다시 돌린다. a2-unmeasured(프록시), unattended(P6), given-answers와
  holes-unknown(fallback)이다. 0.8.0보다 나빠진 must 항목이 없어야 한다.

## 정할 것

1. **`elephant_foot` 값을 모를 때.** 추천: `unknown`을 허용한다. 뜻은 "슬라이서 보정이 켜졌는지 모름"이다.
   그럴 때 모델은 바닥 모서리에 0.3 mm 모따기를 두고(겉모양용, 끼움에 닿지 않는 바깥 모서리만), 전달 때 "슬라이서
   보정이 켜져 있으면 바닥 바깥 모서리가 조금 더 작아진다"고 한 줄 말한다. 대안은 `unknown`을 금지하고 `model`로
   쓰게 하는 것이다.
2. **"알아서 정해 주세요"와 시안 멈춤.** 추천: 위 C의 한 줄을 넣는다. 대안은 초보자 흐름(멈춤 줄이기)에서 함께
   다루고 이번에는 넣지 않는 것이다.
3. **번들이 프록시 build JSON을 담을지.** 추천: 지금처럼 다시 빌드한다(바꾸지 않는다). 상대 경로가 되어도 다시
   빌드하는 편이 판정 재현을 더 확실히 보여 준다. 대안은 담고, REPRODUCE.md의 재빌드는 그대로 두는 것이다.
4. **진행 방식.** 추천: 코드(A, B)는 서브에이전트 하나가 맡고, 총괄이 지침(C)과 골든 비교를 하고 PR 전에 재현으로
   확인한다. 시나리오는 0.8.0처럼 실행 에이전트로 돌린다. 대안은 0.8.0처럼 총괄이 혼자 하는 것이다.

- 초보자 기본 흐름(멈춤 줄이기). 0.8.1 다음에 따로 한다.
